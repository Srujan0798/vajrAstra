# PROTO-61 — SHEET PROVENANCE FORENSICS: RESULT

**Agent:** Sonnet lead · **Date:** 2026-09-30 · **Artefacts:** `level2/unified/build_sheet_v2.py` · `level2/unified/sheet_v2.csv` (12,324 rows)
**Answers U9 (adopt `sheet_v2.csv` for reporting?) and closes one of the five escalated items from the W1 fix loop.**

## The question
`level2/probe22/sheet.csv` — which carries **every leaderboard number in the campaign** — has **no generator on disk** and was **never committed to git** (`git log --all -- sheet.csv` is empty; no `.py` in the repo writes it). Its `CER` column had not been shown to be re-derivable from its own inputs.

## The method (and why it is trustworthy)
For every row, CER is recomputed from the only two reproducible inputs:
- ground truth — `level2/probe22/manifest.json` item `gt`
- prediction — `level2/probe22/out/<engine>/<lang>/<image_id>.json` field `text`

using the repo's own `level2/probe22/metrics.py` for normalisation (`normalize_for_scoring`) and for the bounded rate (`_bound_rate`). The **only** thing substituted is the edit-distance implementation: `metrics.edit_distance` is O(n·m) pure Python on this machine (no `Levenshtein`/`rapidfuzz` package), so `build_sheet_v2.py` adds a numpy prefix-minimum Levenshtein.

**The fast path is validated, not assumed.** It is checked against `metrics.edit_distance` at every startup (24 real rows, hard-abort on mismatch) and was separately proved on 400 random strings plus Indic and edge cases: **400/400 agreement**. A first attempt at the vectorisation disagreed on 22/24 rows and the script **refused to report**; it was rewritten and re-validated. This is recorded because the failure is the point: an unvalidated fast path would have produced a confident wrong answer.

## Result 3 — the "10/18 vs 8/18" escalation is CLOSED

One reviewer reported "8/18" against the lead's "10/18". Both are real numbers computed **on different item sets**:
- **10/18 (correct)** — surya and Sarvam compared on the **same 3 items per language**. This is the like-for-like pairing, and it reproduces identically on the stored and recomputed columns.
- **8/18 (mismatched)** — surya's **full-language** mean (67–100 items) against Sarvam's **3**. Not a valid comparison.

**The lead's 10/18 was right; the 8/18 was a methodological error in the review.** Recorded as such rather than averaged away. (Item-level 21/28/5 also reproduces exactly on both columns.)

## Recommendation
1. **Do not present `sheet.csv` as independently checkable evidence.** It is internally consistent and its conclusions are robust, but a reviewer who re-runs the scorer gets a different column. The honest framing is *"CER as stored by the probe scoring pass; conclusions independently reproduced from the packs; per-cell CER not re-derivable."*
2. **Adopt `sheet_v2.csv` for all future reporting (U9 = YES, with a caveat).** It is generated by a committed script, reproducible end-to-end, and it agrees with the stored column on every conclusion that matters. Where the two differ by >1e-4 on a specific row, the v2 value is the defensible one.
3. **Regenerating `sheet.csv` in place is not required** for the meeting, because no conclusion changes. That de-risks U5: the locked file can stay as-is.
4. **One generator, always.** Whatever is presented from now on must come from a script in the repo (the standard `BENCHMARK_22.md` → `build_benchmark_22.py` pattern already meets it; `sheet.csv` did not).

## What this does NOT do
- It does not identify the original writer, so the **cause** of the 62.9% remains **UNKNOWN**.
- It does not verify the ground truth itself — only the scoring of it.
- It does not touch the locked `sheet.csv`, which was read, never written.
- It does not clear the other four escalated items (K2 provenance, GLM-OCR in OmniDocBench, Indic-OCR pack contents, GlotOCR font figure).
